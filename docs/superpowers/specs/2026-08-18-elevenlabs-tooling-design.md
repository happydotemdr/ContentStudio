# `elevenlabs-tooling` — automated payload execution for ElevenLabs

## Context

Two tool-specialist skills already exist — `elevenlabs-audio` (voiceover) and
`elevenlabs-music` (background beds). Both are deliberately execution-free: each
emits a validated JSON payload and a `curl` template, and states its own boundary
explicitly (`elevenlabs-audio/SKILL.md`: *"This skill does NOT call the ElevenLabs
API. It emits payloads and curl commands; you run them."*). Every VO/bed asset
used by the `stitcher` renders so far (e.g. `stitcher/renders/*/assets/VO*.mp3`)
was generated by a human manually running that emitted curl command — there is no
code anywhere in this repo that holds an **ElevenLabs** API key or issues an
ElevenLabs HTTP call today (a different outbound integration, `discovery_notify.py`,
does hold a Resend key for an unrelated email path — not this one).

The user now has an ElevenLabs API key in their Windows user environment
(`ELEVENLABS_API_KEY`) and a newly trained Professional Voice Clone
(`voice_id: eDwT8Vhp2yxJzAMmuuPA`, 30+ minutes of reference audio) that is now the
pinned channel narrator (`.claude/skills/voiceover-brief/references/channel-voice.md`,
updated 2026-08-18, superseding the previous IVC pin `5kVvcrJnhhULT5LdbshJ`). The
goal is to close the gap between "skill emits a payload" and "audio exists on
disk" with actual, safe, professional-grade automation — without moving the
*creative judgment* (voice pick, settings-per-beat, chunking, prompt craft) out
of the skills, and without weakening the discipline those skills already encode
for handling a Professional Voice Clone correctly.

## Scope

Both `elevenlabs-audio` (TTS) and `elevenlabs-music` (compose) are in scope,
served by one generic mechanism rather than two hardcoded ones — see
"Why one generic command" below.

**Out of scope for v1** (deliberate boundaries, not oversights):
- Streaming endpoints (`/stream`, `compose_stream`, SSE) — actively rejected
  pre-send by E2, not just silently unsupported
- `/v1/music/detailed`'s multipart response (metadata + audio in one response)
  — also actively rejected pre-send by E2
- Batch/multi-payload orchestration — looping over several beats/sections is the
  caller's job (a shell loop, or repeated invocations from a Claude session),
  not this tool's
- Automatic retries
- Cost estimation / dry-run (considered and declined — logging every attempt
  before it fires was judged sufficient)
- Any brief-parsing or payload-authoring logic — that judgment stays entirely in
  the `elevenlabs-audio` / `elevenlabs-music` skills

## Architecture

**Location:** a new standalone package, `elevenlabs-tooling/`, a sibling to
`stitcher/`. It imports nothing from `pipeline_app`, does not read any skill,
and knows nothing about render slugs or stitcher's asset-folder conventions —
matching `stitcher/README.md`'s own stated independence ("imports nothing from
`pipeline_app`, reads no skill, and never opens the corpus"). It has its own
`requirements.txt` (`requests`, `pytest`), its own `README.md`, and its own
`tests/`.

**Why one generic command, not `speak`/`compose`:** `elevenlabs-audio`'s
`POST /v1/text-to-speech/{voice_id}` and `elevenlabs-music`'s `POST /v1/music`
have different URLs and JSON bodies. Both are documented as synchronous POSTs
(neither is a job/polling flow — `elevenlabs-music/references/api-payload.md`
§"The three endpoints"), and the TTS curl template explicitly writes the
response straight to a file (`--output master.mp3`). The music templates in
that same reference don't show a `--output`, so "the compose response is also
raw audio bytes on success" is a reasonable inference from the parallel
`output_format` handling, **not a confirmed fact** — flagged here as the one
architectural assumption implementation should verify with a real test call
against both endpoints before relying on it further (see "Testing"). If music
turns out to need different response handling, the URL/response-shape split
already lives entirely inside `client.py`, so the CLI contract doesn't change.

**What the tool does and doesn't know about endpoints:** it never hardcodes
what a *valid* payload must contain for either service beyond the mechanical
checklist below. It does, however, parse the given `--url` for a small set of
safety and consistency checks (host allowlist, out-of-scope path rejection,
`output_format` presence, and recognizing the pinned narrator's `voice_id` in a
TTS URL specifically for E7) — parsing a URL for these mechanical checks is not
the same as hardcoding an endpoint's required shape, and the distinction matters
because E1/E2 exist for credit and key safety, not endpoint modeling.

**CLI:**

```
python -m elevenlabs_tooling send \
  --url "<full URL including query params, exactly as the skill's curl template gives it>" \
  --payload payload.json \
  --output out.mp3 \
  [--timeout SECONDS] \
  [--force]

python -m elevenlabs_tooling validate \
  --payload payload.json \
  --url "<same URL>"
```

`--url` is always the complete URL the skill already produced (base path +
query string).

**`--output` safety:** refuses to overwrite an existing file unless `--force`
is given — a plain file-safety default (avoiding an accidental silent respend
over an already-generated asset from a typo'd re-run), distinct from the
cost-guardrail flags (dry-run, `--confirm`) that were considered and declined
earlier. The parent directory of `--output` must already exist; the tool does
not create directories.

**Auth:** `ELEVENLABS_API_KEY` read from the environment (already set by the
user), sent as the `xi-api-key` header alongside an explicit
`Content-Type: application/json`. No key file fallback (unlike
`discovery_notify.py`'s `RESEND_API_KEY` + `resend_api_key.txt` pattern) — an
env var is sufficient here and keeps the tool from ever writing key material to
disk. The key is checked **after** validation, not before (see "Order of
operations"), so a broken payload's findings are never hidden behind a
missing-key error.

## Order of operations (`send`)

1. Read `--payload` and confirm `--url`/`--payload` are both given and the
   payload file exists → `EXIT_UNREADABLE_INPUT` otherwise.
2. Parse the payload file's bytes as JSON. Must parse *and* be a JSON object
   (not a bare list/string/number) → `EXIT_UNPARSEABLE` otherwise, the same
   code Gate C reserves for "read but structurally unusable"
   (`scripts/lint_prompt_sheet.py`'s `EXIT_UNPARSEABLE`).
3. Run the full validation checklist (below) against the parsed payload and
   the `--url`. Every check runs; findings accumulate (never stop at the
   first one — same principle as `stitcher/stitcher/preflight.py`). Any `E#`
   finding → print all findings, `log("validate.rejected", ...)`,
   `EXIT_FINDINGS`, nothing sent. `W#` findings print but never block.
4. Only now: check `ELEVENLABS_API_KEY` is set → `EXIT_NO_API_KEY` otherwise.
5. Check `--output` doesn't already exist, unless `--force` → clear error
   otherwise (not a new exit code; reuses `EXIT_USAGE`, since this is a CLI
   invocation error, not a payload or send problem).
6. `log("send.attempt", ...)` written **before** the network call (timestamp,
   `--url`, the payload file's path and a content hash, `--output` path) —
   matches `stitcher/stitcher/ffmpeg.py`'s "every command is appended to the
   log before it executes."
7. `POST` to `--url` with `xi-api-key` + `Content-Type: application/json`
   headers, the **raw bytes** read in step 1 as the body (never
   re-serialized — see "HTTP call" below), bound by `--timeout`.
8. **2xx + `Content-Type` starts with `audio/`:** those bytes written to
   `--output`; `log("send.success", ...)`; exit 0.
9. **2xx but `Content-Type` doesn't start with `audio/`:** credits were
   already spent, so the bytes are not discarded — written to
   `<output>.unexpected` instead, with a clear message explaining why nothing
   landed at the intended path; `log("send.failed", ...)`;
   `EXIT_SEND_FAILED`.
10. **Non-2xx or network/timeout error:** nothing written anywhere; the error
    body or exception message printed and logged;
    `log("send.failed", ...)`; `EXIT_SEND_FAILED`.

`validate` runs steps 1–3 only, against `--payload`/`--url`, and never touches
the network or the API key.

## Validation (the hard gate)

Structure matches `scripts/lint_prompt_sheet.py` (Gate C) — the other
standalone, dependency-free CLI validator in this repo — rather than
`pipeline_app/gates.py`, which is wired into that subsystem's stage/artifact/
upstream orchestration (`StageDef`, `UpstreamMap`) and doesn't apply to a tool
with no concept of a "stage" or "upstream artifact."

```python
@dataclass(frozen=True)
class Finding:
    check: str     # "E1".."E14" (blocking) or "W1"/"W2" (informational, never blocks)
    message: str
```

**URL checks (run first, always):**

| Check | Rule |
|---|---|
| E1 | `--url`'s host must be exactly `api.elevenlabs.io` — never send the API key anywhere else |
| E2 | `--url`'s path must not target a v1-out-of-scope endpoint: `/stream`, `/compose_stream`, `/music/detailed`, `/compose_detailed`, `/compose_detailed_stream` (case-insensitive) |

**Payload-shape check:**

| Check | Rule |
|---|---|
| E3 | the payload is either TTS-shaped (non-empty `text`) or music-shaped (exactly one of `prompt` / `composition_plan`) — never both shapes' distinguishing fields, never neither |

**Common field checks:**

| Check | Rule |
|---|---|
| E4 | `model_id` must be present and non-empty (`elevenlabs-audio/references/api-payload.md`: "Always set explicitly — the default is not the flagship") |
| E5 | `voice_settings.speed`, if present, must be in 0.7–1.2 |
| E6 | zero-retention/stitching conflict: `--url`'s query has `enable_logging=false` *and* the payload has `previous_request_ids` or `next_request_ids` — `enable_logging` is a query parameter, not a payload field, so this check reads the URL, not the payload body |
| E7 | if `--url`'s `voice_id` path segment is the pinned narrator (`eDwT8Vhp2yxJzAMmuuPA`) and `model_id` contains `v3`, the payload must explicitly include `use_pvc_as_ivc` as a boolean (either value accepted). **Known limitation, stated plainly:** this only proves the key wasn't silently omitted — it cannot verify the choice was deliberate, and it does not (and should not) fire when the payload routes around the trade-off entirely by using `eleven_multilingual_v2` instead of a `v3` model, which is the third option `channel-voice.md`'s Open action 3 names. |
| E8 | `pronunciation_dictionary_locators`, if present, must have ≤ 3 entries |
| E9 | `previous_request_ids` / `next_request_ids`, if present, must each have ≤ 3 entries |
| E10 | `seed`, if present, must be an integer in 0–4,294,967,295 |

**Music-shaped only** (from `elevenlabs-music/references/api-payload.md`'s
parameter-conflict table — each of these "either 400s the request or silently
no-ops," which for a paid generation call means a wrong result gets billed):

| Check | Rule |
|---|---|
| E11 | `seed` must not be present together with `prompt` (plan-only field) |
| E12 | `force_instrumental` must not be present together with `composition_plan` (prompt-only field) |
| E13 | `music_length_ms` must not be present together with `composition_plan` (prompt-only field) |
| E14 | if `composition_plan.chunks` is present, `model_id` must equal `music_v2` (chunk plans require `music_v2`) |

**Warnings (never block):**

| Check | Rule |
|---|---|
| W1 | `--url` has no `output_format` query param — a default applies, but the skill's own doctrine is to state the value chosen rather than leave it implicit |
| W2 | `voice_settings.similarity_boost`, if present, > 0.9 — a craft-quality concern, not an API constraint (the API accepts 0–1). Two different repo-documented thresholds exist for this, cited honestly rather than merged into one: `voiceover-brief/references/voice-selection.md` and `settings-by-content-type.md` warn against >90% ("over-enunciated 'news anchor' artifacts"); `elevenlabs-audio/references/voice-settings.md` separately flags "above ~0.85 risks reproducing noise present in the reference audio," marked `[T-unverified]`. Because the two disagree and neither is a hard API limit, this is a warning, not a block. |

**Exit codes**, adapted from Gate C's taxonomy (2 stays argparse-only, per
`lint_prompt_sheet.py`'s explicit rule that "argparse owns 2 unconditionally, so
nothing else may use it" — the missing-API-key case gets its own code instead):

```
0  EXIT_PASS               validation clean / send succeeded
1  EXIT_FINDINGS           blocking (E#) errors found — the payload is the problem
2  EXIT_USAGE              argparse only, or a CLI-level problem (e.g. --output exists without --force)
3  EXIT_UNREADABLE_INPUT   payload file or --url missing/unreadable
4  EXIT_UNPARSEABLE        payload file is not valid JSON, or is valid JSON that isn't an object
5  EXIT_SEND_FAILED        validation passed but the live API call failed, or returned an unexpected content-type
6  EXIT_NO_API_KEY         ELEVENLABS_API_KEY not set (checked only after validation passes)
```

## Logging and error handling

**Logging** — `elevenlabs_tooling/log.py` exposes `log(event, *, level="info",
**fields)`, mirroring `pipeline_app/obs.py`'s `log()` shape (structured JSON
line to stderr *and* appended to a dated file, here
`elevenlabs-tooling/logs/tooling-YYYY-MM-DD.log`) without importing
`pipeline_app`. One invariant carried over exactly: **logging never raises** —
every I/O boundary (the stderr write, the file write) is wrapped so a failure
to log can never mask or interrupt the thing being logged, matching
`obs.py`'s stated contract verbatim. Events: `send.attempt` / `send.success` /
`send.failed`, `validate.passed` / `validate.rejected` (a rejected payload is
logged too — full audit trail even for attempts that never reached the
network).

**HTTP call** — `requests.post(url, headers={"xi-api-key": key, "Content-Type":
"application/json"}, data=payload_bytes, timeout=SEND_TIMEOUT_S)` →
`response.raise_for_status()` → catch `requests.exceptions.RequestException`
specifically (not bare `Exception`), matching `discovery_notify.py`'s
`send_email` precisely on this point. `payload_bytes` is the **raw bytes read
from `--payload`**, sent unmodified — validation parses those same bytes as
JSON to inspect fields, but never re-serializes them for the actual send, so
what was validated is byte-for-byte what gets POSTed (the same reasoning
`elevenlabs-audio/references/api-payload.md` gives for `-d @payload.json` over
an inlined string).

**Timeout precedence:** `--timeout` (if given) overrides
`ELEVENLABS_TOOLING_TIMEOUT_S` (if set and valid) overrides the 300-second
default. An invalid value at either level (non-numeric or non-positive) warns
to stderr and falls back to the next level — this now matches
`stitcher/stitcher/ffmpeg.py`'s `_timeout()` behavior exactly (env override,
warn-and-fallback on a bad value), extended with one additional CLI-flag tier
`ffmpeg.py` doesn't have. 300 seconds is sized to comfortably cover music
composition (the slower of the two endpoints) without ever firing on a
legitimate call, mirroring how `FFMPEG_TIMEOUT_S`'s hour-long bound was sized
against real encode times rather than picked arbitrarily.

**One deliberate divergence from `discovery_notify.send_email`, stated
explicitly:** that function swallows failures and returns `False`, because
sending a notification email is a best-effort side effect of a run that
already succeeded. That does not fit here: sending *is* this tool's entire
purpose, so a failure propagates to a non-zero exit (`EXIT_SEND_FAILED`)
rather than a silent `False` — the caller must see it fail.

On failure, a prefixed stderr line matches the existing convention (e.g.
`discovery_notify: send_email failed: {exc}`) — here,
`elevenlabs_tooling: send failed: {exc}`.

## Testing

`elevenlabs-tooling/tests/`, pytest, matching `stitcher`'s and the root
suite's convention:

- One test per validation check (E1–E14, W1–W2): a minimal valid payload for
  each shape (TTS, music-via-prompt, music-via-composition_plan), then one
  targeted mutation per test that should trip exactly that check and no other.
- CLI/send flow tested with the HTTP layer mocked (`unittest.mock` — no real
  network calls in the test suite; this is a paid API). Covers: success,
  non-2xx, timeout, unexpected content-type (quarantine path), missing
  `ELEVENLABS_API_KEY`, `--output` already exists without `--force`.
- A logging test confirming both a rejected (validation-failed) attempt and a
  sent attempt each produce a log entry.
- **Before relying on the music/TTS response-shape symmetry**, one manual
  (not automated — costs real credits) verification call against both
  `POST /v1/text-to-speech/{voice_id}` and `POST /v1/music` confirming both
  return a direct `audio/*` response body on success, per the open assumption
  flagged in "Architecture." If music's compose endpoint turns out to need
  different handling, only `client.py`'s response-parsing branch changes —
  not the CLI contract.
